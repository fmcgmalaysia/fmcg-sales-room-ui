CMS现有做法审查：先找根本问题

2026-11-03 · 后台只读第一轮 · 没有修改生产代码、CMS或发布

此前局部查找优化暂缓。审查目标调整为：日常读写是否依赖全部历史、每个业务动作新增多少记录、哪些重复内容可避免，以及跨月未结事项如何接续。不能以代码运行更快代替长期容量方案。

证据范围

依据当前checkout相关源码、既有Wix准确读回记录、11月3日400条原生CMS导出及8项未修改模块边界检查。本轮未取得新鲜Wix代码，代码风险不冒充新的线上复现；没有全站扫描或容量承诺。Wix具体套餐上限、实际每日增长与真实网络耗时仍未知。

优先级发现证据等级位置问题与边界整改要求

待验证无实质改变也可能保存新修订潜在问题，尚无现场复现purchaseOperations.js:PLAN costing/patch/no-change guard已有无变化拒绝逻辑，不能说系统完全没有防重复；但costing分支无条件填充patch，可能绕过依赖patch为空的判断。构造相同成本计划重复提交场景，区分确认动作、变化内容及新请求。没有证据前不删除历史或断言已发生。
P1历史保留与当前业务仍强绑定8项只读边界验证及代码依赖purchasePlan.js、warehouseReceiving.js、customerAllocationContext.js、supportDesk.js只取最新采购/收货事件会报错；旧批次可能仍有库存、欠款、借货或文件身份。按月移动不能自动解除依赖。先定义当前状态、未结事项、月结接续和历史更正，再确定归档资格。月份只能组织历史，不能决定业务结束。

已经有保护的部分，不能重新发明或误删

普通页面GP读取已无写入；400条样本没有GP或MOVE ROW事件；38条Desk事件没有完全相同的前后状态。采购PLAN已有无变化判断，保存恢复使用原请求。这些事实说明不能把所有Activity或所有重复点击都归为浪费。

从本轮发现吸取的教训

  1. 界面分页、隐藏历史或静默刷新，都不等于后台读取成本下降。
  2. 恢复机制必须有明确生命周期和最少证据，但精简前必须核清所有消费者。
  3. 局部修补应同时记录查询量、计算量及存储增长，否则只是把瓶颈转移到别处。
  4. 不得仅因出现旧模块或索引就认定它正在生产使用；例如AccountReadIndex有维护代码，但当前已读查询函数仍先重建所有行，其线上启用及生命周期需要单独核实。
  5. 全站不同端点各自修好，并不证明一次完整用户动作没有重复读取或不一致快照。

下一步推演顺序

  1. 给真实动作建立增长预算：开单、采购修订、收货、借还货、Loaded、SI、付款分别统计新增业务行、恢复行与内容体积；只读应无业务写入，已授权的付款已读确认需另计。
  2. 定义每天必须读取的当前状态和未结责任，列清唯一权威及历史更正路径。
  3. 定义月结核对、跨月接续和归档资格。不能仅按月份删除，也不能把同站换集合当减少总行数。
  4. 再决定查询、保存和历史保留的最小实施顺序，先场景验证，再核对Wix并修改。

Buyer下载/身份、Chrome加载及其它未结任务仍留在原工作账；本审查没有替它们结案。当前尚未选择或实施新的状态存储、归档集合或回执压缩机制。
