结论与决定

关联历史索引确实较少维护一份当前结果，值得作为第一步候选；但它只能排除无关历史，不能消除同一任务自身的版本链增长。固定当前结果能进一步限制读取量，却需要额外记录、写入和覆盖全部保存入口。不能用“较少机制”或“读取次数固定”单独决定上线。

先完成关联范围及完整性检查的最小设计，并核对真实索引能力。只要较小路线达到实际工作量要求，就不引入当前结果存储。当前结果方案保留为离线备选；不并行部署两条业务权威，也不在日常页面静默退回全历史。

上表是已查明的必要边界，不是对整个仓库所有写入入口完成可达性审计的声明。下一步应先收敛到一个具体只读消费者，以其全部依赖为验收范围；不要一次迁移全站。

遗漏检测与页面一致性：上线前不能跳过

  1. 查询只能找到有正确关联字段的记录。完整性依据必须来自查询结果之外的可靠证据，或经核对的回填与全部写入入口；仅检查已返回记录的版本链不能发现整次尾部遗漏。
  2. 待完成查询前后均为空，不证明期间没有提交。页面涉及多个根任务时，必须定义所需的一致性范围，再设计验证；不能假定一个通用“读两次”即足够。
  3. 后台保存应继续核对最新业务版本，页面一致性验证不能代替保存校验。
  4. Wix 实际索引、consistentRead 行为、本站配额和生产读回尚未验证。先只读核对，任何索引创建、回填或新存储写入需具体批准。
