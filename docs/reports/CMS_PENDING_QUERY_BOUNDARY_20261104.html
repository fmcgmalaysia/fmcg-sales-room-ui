CMS 采购读取与保存回执边界

2026-11-04 · 后台离线核对 · 基准 3ea8672

本轮没有修改正式程序、CMS 数据或索引，也没有发布。8 组诊断完成，其中包含刻意复现不安全做法的反例；不能将“诊断通过”理解为这些风险已经修复。

发现优先于性能改造的具体风险：合并 PO 部分保存失败后，原货仓保存函数仍接受 20 箱收货；恢复原合并请求后，PO 内部 ID 改变，新 PO 收货页显示 0。原收货事实仍存在。本例在离线内存中复现，不代表正式数据已发生此问题，也没有据此认定库存被删除。

决定

暂不采用“固定当前结果”作为下一步上线方案。优先把采购事实及保存回执与任务的关系查清楚，再评估按关联读取。不能只以月份截断、只读最新记录、看到锁为空就跳过回执，或在仍读全历史的页面额外增加一条明细查询。

现有记录不需要被删除才能减少读取。对采购计划而言，许多其他部门的回执属于读取范围过宽，并不等于这些回执本身应该删除。容量减少仍是另一项未完成的工作。

场景实际结果结论
价格从 16 改成 32，任务更新后失败处理锁已释放。原完整证据返回已确认的 16 并标待恢复；省略 PREPARED 后却返回 32，且没有待恢复提示。锁为空不代表完整。不能靠锁决定是否查询准备回执。
采购事实已全部写齐，仅 RESULT 插入前失败价格 32 可正常确认，无待恢复；原请求重试只补 1 条 RESULT。不能把缺 RESULT 全部当作业务未完成，更不能重复提交新交易。
两个任务合并 PO，其中一个任务写入前失败一个任务已带 PO，另一个未带；锁已释放。PLAN 专用读取器待恢复数为 0。原请求可恢复两个任务。PLAN 专用保护不能被宣传为覆盖全部合并 PO 的保护。其他保存入口是否允许错误操作，需要独立验证，不能仅据此断言全部入口失守。
增加 50 箱供应来源，最后接受来源事件前失败新任务和两份来源份额已存在，但 SOURCE_ADDED 尚未存在；锁为空，PLAN 专用待恢复数为 0。原请求可恢复。关联范围必须能从 PREPARED 中的未来任务、父任务取得，不能只从已接受来源发现。
合并 PO 中断 → 货仓收 20 → 恢复原合并请求原采购、PO 投影、货仓读取及收货保存均执行成功；恢复前显示 20，恢复后两个成员的 PO 使用另一内部 ID，显示 0，Activity 中的收货记录仍为 1 条。已经不只是提示缺失：可执行的下一步会与后续恢复冲突。必须先保护部分提交的 PO，不能仅靠查询加速。测试也执行了货仓入口附带的客户待备货、备货和 CBM 读取，但未包含真实 Wix 认证、页面网络或生产时延。
只给采购计划计算器提供 PLAN 准备回执排除快照里 81 条其他准备回执后，模拟中断的已确认任务与待恢复结果一致。仅证明这个函数的类型边界；不是完整 Purchase 页面、Desk、文件或库存的查询替代方案。

原请求恢复后再次重试没有新增重复业务记录。合并 PO 的任务更新本身并行执行；首轮故障注入误以为“第一条返回异常后第二条不会完成”，已修正为明确让指定成员在落库前失败。此修改只在诊断脚本，没有改变生产并发流程。

当前后台源码中，除采购计划外，Desk 恢复（deskDelivery.js）、短装恢复（shortloadResolution.js）、客户文件验证（customerAccountLedger.js、customerFulfilmentService.js、supportWorkroom.web.js）及旧排序记录读取（purchaseDisplayOrder.js）还使用准备证据。这里只列实际引用，不表示这些入口都在当前页面执行，也不授权清理旧排序实现。

下一步最小范围

  1. 先处理已复现的合并 PO 中断保护，需确认新增修补范围。复用现有保存完整性判断及相关单据的待恢复标记，阻止该次合并涉及的来源和目标 PO 在未完成时继续收货等依赖操作；无关 PO 继续工作。保留原请求恢复，不以新请求重做。新增供应来源目前只确认读保护未覆盖，不把它默认为已经复现同样的货仓故障。
  2. 核实正式 NCT/GHR 索引和线上消费者，提出准确的一项索引调整方案。当前没有可直接追加普通索引的空间。
  3. 若选择按任务关联查询，只在同一次原始事实或 PREPARED 写入中声明关联，不另建第二套库存账。历史关联回填必须先预览、检查覆盖并获得具体批准；缺失关联不可当作无记录或零。
  4. 候选与原读取逐任务对账，覆盖跨月、合并 PO、未来来源、中断和重试；再测真实 Wix 查询耗时。正常页面不能长期同时跑两套计算，也不能悄悄退回全历史。

待批准的最小修补范围

单一目标：合并 PO 未完整提交时，不能以暂时的成员集合生成可继续操作的采购单；原请求恢复后，正常收货和编号保持一套既有逻辑。

  • 预计检查及必要最小修改：purchasePlan.js 的共同完整性判断、purchaseProjection.js 的待恢复传播、purchaseOperations.js 的原请求恢复边界；现有货仓保护在 warehouseReceiving.js，只有证据证明共同标记不能覆盖时才提出额外修改。所有正式修改前重新核对 Wix 原件。
  • 受保护行为：正常单项和合并开 PO、财务已付款锁定、旧 PO 收货、原请求幂等恢复、已完成历史、公司隔离。不能放宽任一保存保护来让重试通过。
  • 测试必须包括：写任何成员前中断；写一部分成员后中断；部分事件写入后中断；事实完整而 RESULT 缺失；向已有 PO 合并；原请求恢复与再次重试；无关 PO 可继续收货；NCT/GHR 隔离；历史已完成操作不误锁。
  • 不改变 PO ID 算法、锁存储、付款、库存账、归档或索引，不新增当前结果集合，不补写或删除正式历史。若已有正式记录发生关联问题，另列证据和修复范围，不自动迁移。
  • 恢复点：沿用已验收 D04 正式基准及本轮修改前的新鲜 Wix 原件。当前诊断分支不是正式恢复版本。

需要具体批准的依据：项目 AGENTS.md 要求 If the required scope expands, stop and obtain explicit approval for the new scope. 本轮原本是查询范围验证，以上是已复现风险对应的业务保存保护修补。此处只提出范围，尚未修改生产代码。

即使关联查询成功，单个任务自身的历史仍会增长；它降低无关历史读取，不减少 CMS 条目总数，也不能据此承诺百万行性能。归档或减少重复事实需另有引用审查、恢复验证和明确范围。
