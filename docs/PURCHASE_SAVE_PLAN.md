# Purchase 保存机制只读审查与改进方案

2026-10-14。状态：方案，未实现、未发布。当前 Purchase 正式页面可读取5条任务；未点击 Save、未更改业务记录。最近一次实际 Save 失败的操作和错误原文仍待用户补充。

## 已证实的问题与未证实的原因

`purchase-live/app.js` 用全局 `savePending` 管理一笔保存。保存或回执核对未完成时，导航和公司切换被阻止，多项操作直接返回，弹窗字段被冻结。30秒后查询回执，之后最多两次10秒间隔重查；回执始终没有取得时保留原操作，允许重试，却仍保留全局限制。这解释了用户为什么可能被困住，不证明所有实际失败都由超时导致。

`integration/wix/purchase-room-page.js` 将抛出的异常主要转换为一段错误文字。`integration/backend/purchaseOperations.web.js` 只把指定列表里的业务验证错误作为结构化失败返回，其余异常重新抛出。核心模块中例如“Check supplier costs and discounts.”、“A procurement reason is required.”等提示未在该列表中；它们经过 Wix web method 后可能失去具体信息。必须用实际日志验证，不能直接认定这是本次故障。

前端通过错误文字的正则表达式区分“确定失败”和“结果不明”。泛化的 `Unable to handle` 会进入回执核对路径；如果服务器实际在验证阶段拒绝且没有成功回执，界面无法仅凭回执缺失区分它与仍在处理。`getPurchaseSaveResult` 对缺失结果统一返回 pending。

另外，`purchaseOperationJournal.js` 的锁按 `company + /PURCHASE` 范围建立，成本写入另有任务锁。因此“同时保存所有不同任务”不是一个纯前端小补丁。初期应保持当前后端串行写入，允许浏览与独立草稿工作；不能承诺并发提交而不处理现有锁。

## 必须保留

- 原请求ID、相同请求安全重试、成功回执确认、PREPARED/RESULT审计与已有恢复机制。
- 版本冲突检查、发票锁定、Staff权限、NCT/GHR隔离。
- 供应商、采购数量、五个成本字段在 PLAN 中成组提交，原数量和成本公式不变。
- P.O.、收货、分货、付款、客户反馈等业务动作的既有约束和审计原因。
- 已有 sessionStorage 草稿恢复。它不是跨设备或永久保存保证；不另建第二套业务存储。

## 建议交互

专业工具会减少普通编辑的手动保存，但仍区分编辑与正式业务动作。Microsoft Power Apps 对已有记录默认自动保存，并明确提醒既有保存触发工作流可能不适合直接自动化：
https://learn.microsoft.com/en-us/power-apps/maker/model-driven-apps/manage-auto-save

| 操作 | 建议 |
|---|---|
| 不产生业务承诺的普通资料编辑 | 有效字段完成后自动保存；建议短暂防抖，Enter可立即完成。具体字段先列出副作用再启用 |
| 普通排序 | 完成一次拖动后自动提交排序，不要求额外Save；冲突时保留原顺序草稿 |
| 相互依赖的价格与折扣 | 编辑时本地预览，完整有效组合才提交；不能每敲一位数字都写CMS或拆开原原子操作 |
| Supplier Plan：供应商、数量、价格 | 草稿可连续编辑；一次明确的“Apply Purchase Plan / 应用采购方案”提交整组，不因选择一个供应商就强迫先Save |
| P.O.确认、减少数量、分货、短缺决定、提交文件等 | 保留明确动作和所需核对，例如Confirm P.O.，不能自动执行正式采购承诺 |

自动保存只在服务器确认后显示“Saved”。尚未发送显示“Unsaved”，发送中“Saving”，回执未知“Checking result”，确定失败“Not saved”，版本冲突“Review changes”。界面保留最后确认时间。用户继续输入时，成功回执只能清除这次发送的草稿，不能清除后来输入的内容。

失败必须包含：产品/条码或P.O.、字段、具体原因、输入是否保留，以及可执行的下一步。例如“955… · Disc.3超过折后成本；改为≤XX后重试”。这是文案示例，不能在未知结果时编造数值或宣称未写入。

确定验证失败：字段旁标红并聚焦，允许改正。网络/回执不明：保持同一请求ID，先核对，不能宣称失败后生成新操作重复提交。版本冲突：显示服务器最新值和草稿值，用户选择重新应用，禁止静默覆盖。

只限制当前记录及依赖其结果的正式动作，允许浏览、搜索和无关记录的草稿工作。后台目前为公司级串行锁，提交仍需遵守该限制；不能通过取消请求或强行删除锁来“解锁”。关闭面板可保留待核对操作并显示待处理入口；此行为需要前端上下文/草稿隔离验收后才能实现。

## 最小实施顺序

1. **错误可定位**：取得实际失败日志，完整比对当前 Master 草稿/线上代码与仓库；先修正必要的错误回传，使已知验证失败明确指出字段/任务。未知服务器异常保留追踪ID和回执核对。单独分支，不同时重构journal。
2. **避免全工作间锁死**：保留串行提交、同请求恢复，只解除浏览限制并实现有上下文的待处理入口。验证导航、草稿、刷新、迟到回执及公司隔离，不直接允许并发写。
3. **逐类自动保存**：先排序和经确认无额外业务承诺的字段；PLAN、P.O.及正式业务动作保持成组确认。核实审计/GP/财务Checked等联动，不能把显示改动当作无副作用写入。
4. **Purchase 视觉统一**：独立样式任务继承 `MASTER_WORKROOM_STANDARD.md`。之后 Account/Warehouse/Support逐个推广，保持现有业务数据流。
