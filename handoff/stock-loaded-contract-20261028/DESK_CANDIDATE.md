## User-visible scenarios

1. Support starts at Customers and clicks ENTRY. Orders navigation is hidden. The current Desk workroom, PO No., SO No., document uploads, invoices, customer profile and Desk1/2/3 remain in the existing workroom. The separate Packing link is removed.
2. Within one Desk, Send to Warehouse authorizes exactly the displayed, actually allocated remaining cartons. It does not receive stock, allocate extra cartons, or deduct stock. Unallocated quantities, stale Desk revisions, another customer's rows and an invoice-locked Desk are rejected. The existing Desk revision chain serializes authorization against concurrent task moves.
3. Warehouse Delivery Task shows only authorized customer+Desk instructions, with Support-style task columns. Loaded is the only editable quantity. Orange shows the authorized default before confirmation; it is not actual Loaded. The compact modal accepts actual cumulative Loaded, reasons, notes and optional photos. Shortfall requires a reason; Other requires a note. Actual confirmed zero remains a real shortfall.
4. Confirm prepares the local evidence and queues the operation, then closes the modal so the employee can handle another row. The isolated browser measured65ms before the next task was available in the final run, while the synthetic first receipt was delayed1.8seconds. This is a test measurement, not a production latency promise. Actual quantities change only after the matching server receipt. Queued rows use the last confirmed list revision; no full CMS workspace reread is required between confirmations.
5. An unknown result pauses subsequent writes and offers Retry same save with the identical request ID and payload. A definite validation failure retains queued quantities, reasons, notes and photos in this window for correction after refresh. Closing a window with pending writes triggers the normal browser warning. Warehouse photo bytes stay out of the CMS journal. An interrupted prepared Support authorization can be restored only to its original employee with its original digest/request.
6. Confirmed Loaded uses the existing physicalOutflow source attribution and operation journal. Invoice and Dispatch do not deduct again. In the two-line isolated scenario150physical cartons remain150after authorization, then80+50actual Loaded leave20. Lost acknowledgement and retry do not deduct twice. A later cumulative correction from80to90 deducts only10; an ordinary decrease is rejected.
7. Confirmed differences produce red Loaded capsules in Warehouse, Support and Purchase. Read-only capsules use pale backgrounds; the editable Warehouse bubble remains solid. Saved photos keep the existing Drive viewer mechanism. IDs-only invalidation asks Support to reread canonical facts; it never supplies a quantity. Purchase retains its existing guarded refresh mechanism and finance locks.
8. Old no-Desk index, synthetic draft and standalone Packing URLs become replacement redirects to the Desk entry. Standalone bookmarks go through the real Wix Support page. Nine exclusive executable/style resources are absent from the92-resource package. Shared draft.css/draft-compact.css remain byte-identical. Repository history and existing CMS evidence are not deleted. The service rejects old standalone planning writes; cached Warehouse PACK/LOAD cannot bypass Desk authorization.

## Remaining limitations and decisions

- Authority to resolve/clear a shortfall was never defined. There is no arbitrary clear-red action. A real additional authorized loading may close the quantity gap; physical returns, damage write-offs and reductions of already confirmed Loaded need their separately defined correction workflow.
- Photo-mandatory conditions were never finalized. Photos are optional here, up to3per confirmation and2MBtotal, using the existing file service. This does not claim all categories require a photo.
- The separate Support remainder split/cancel phase and complete partial-Desk invoice handling are unfinished. Existing invoice protection may require splitting unloaded quantities before invoice confirmation; this candidate does not remove that guard.
- Borrowing debt, cross-month reconciliation, stocktake/month closing and CMS/Drive historical archiving remain outside this candidate. No historical rows or source facts were deleted.
- Failed Warehouse input/photos are retained in the current window, not durable across forced browser termination. An unknown receipt must be reconciled through its original request; do not invent a replacement physical outflow. Ordinary browser refresh/close warns while pending.
- Real transactions, real photo delivery permissions, public usability and user acceptance remain pending after the coordinated Wix/Pages release. Passing local tests cannot substitute for those stages.
